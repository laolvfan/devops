# ADR-005：超时由调用方按任务设置

- 状态：暂定，待 A11 确认
- 来源：E2 需求与接口契约；B11 当前提案

## 背景

不同项目和任务的构建、分析时间差异较大。为所有任务设定固定超时，可能导致部分任务被过早终止或等待过久；预先多次试运行也会增加构建成本。

## 决策

- 所有任务都由调用方提供正整数 `timeout_seconds`，不设统一默认值。
- 调用方根据任务类型、项目规模和运行资源选择保守上限。
- 计时从 `started_at` 开始，不包括排队时间。
- 超时后任务状态为 `TIMED_OUT`，错误码为 `EXEC_4002`。
- 重试时建议提高超时值并创建新的 `job_id`，沿用原 `trace_id`。
- 不通过额外的重复试运行来估算超时。
- 接口样例中的 `1800` 秒是示例值，不是默认值。

## 备选方案分析

- **为所有任务设统一默认值**：调用方更简单，但无法适配任务和资源规模差异，也可能掩盖过小或过大的限制。
- **要求先重复试运行再估算**：可能帮助估计耗时，但增加构建成本，且历史耗时不能保证下一次运行时间。
- **将排队时间计入执行超时**：规则较简单，但长队列会在任务实际开始前消耗执行额度。

## 后果

- 每次创建任务都要明确给出超时值。
- 超时值可能因调用方选择不同而变化，需要随任务记录实际值。
- 实际执行耗时由 `execution.duration_ms` 记录。
- 调用方选择的上限不保证任务必然在该时间内完成；超时语义需由服务端一致执行。

## 待确认

- A11/B11 确认是否将“重试提高超时值”纳入跨组正式规约。
- 契约应校验请求 `input.timeout_seconds` 与响应 `execution.timeout_seconds` 的对应关系。
